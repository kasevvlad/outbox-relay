# Ограничения и что можно улучшить

## Как минимум один раз, а не ровно один

Дедупликация JetStream работает только в окне 2 минуты. Если relay упал после отправки и пролежал дольше — после перезапуска сообщение уйдёт повторно, и JetStream его уже не узнает. Подписчики должны быть готовы к дублям и проверять `Outbox-Id`.

## Порядок только при одном relay

Один relay отправляет строго по `id`. Если запустить два, первый возьмёт строки 1–100, второй 101–200, и они отправят их параллельно — порядок между пачками перемешается. Для событий одного заказа это может быть важно. Варианты: запускать один relay (и перезапускать при падении), или выбирать «лидера» через advisory lock в Postgres, чтобы работал только один, а второй ждал на подхвате.

## Порядок по id — не совсем порядок коммитов

`id` выдаётся при вставке, а не при коммите. Если транзакция A получила id 10 и коммитится долго, а транзакция B получила id 11 и закоммитилась быстро, relay может отправить 11 раньше, чем увидит 10. Для строгого порядка в рамках одного заказа обычно хватает того, что события одного заказа пишутся последовательно.

## Одна «битая» строка блокирует всё

Если какое-то сообщение не может уйти никогда (например, `event_type` с пробелом даёт недопустимый subject), relay будет каждый раз останавливаться на нём, и все следующие события застрянут. Нужен счётчик попыток и перенос таких строк в отдельный статус, как dead letter, — по аналогии с webhook-relay.

## Отправка по одному сообщению

Каждое сообщение отправляется отдельно и ждёт подтверждения. Это просто и сохраняет порядок, но медленно: при сотнях событий в секунду упрёмся в сетевые задержки. JetStream умеет асинхронную отправку (`PublishMsgAsync`) с ожиданием всех подтверждений в конце.

## Опрос базы

Relay спрашивает базу раз в `POLL_INTERVAL`, поэтому событие может задержаться до секунды. Можно добавить `LISTEN/NOTIFY`: триггер на вставку в outbox будит relay сразу. Или читать изменения прямо из WAL Postgres (так делает Debezium), но это совсем другой уровень сложности.

## Таблица только растёт

Отправленные строки не удаляются. Нужна периодическая чистка, например `DELETE FROM outbox WHERE published_at < now() - interval '7 days'`.

## Нет метрик

Главная метрика для outbox — сколько строк ждут отправки и сколько лет самой старой из них. Если число растёт — relay не справляется или лежит. Сейчас это видно только запросом к базе.
